# ReyOS — Known Open Bugs

Bugs that are confirmed real but not yet fixed. See `fixes.md` for the ones that *are* resolved.

This file was rewritten from scratch on 2026-08-18 after a full audit of the working tree (most of the source had drifted weeks ahead of the previous version of this doc, which still described things that were already fixed or no longer applied). Anything not carried forward from the previous version was either confirmed resolved (moved to `fixes.md`) or could no longer be confirmed as still true and was dropped rather than carried forward as stale guesswork.

## ReyOS Browser: PDFs always download instead of viewing inline

Confirmed live (2026-08-19) against two different real PDF URLs, including Mozilla's own pdf.js test file (specifically used to verify inline PDF rendering, ruling out a bad test file or a server forcing `Content-Disposition: attachment`): navigating to a PDF always triggers the download flow, never the browser's built-in viewer. `settings.pdfViewerEnabled: true` is already set on the `WebEngineView` (correct API for this) and makes no observable difference. Working theory, not confirmed: the PySide6 wheel's bundled QtWebEngine (6.11.1) may not actually ship the PDF viewer plugin binary, making the setting a no-op regardless of value — would need inspecting the actual Qt WebEngine build contents to confirm, or trying a JS-based `pdf.js` redirect as a workaround instead of relying on the native viewer.

## Launched apps sometimes never get a taskbar entry, on a real fresh install

Confirmed live (2026-08-24) on a genuine fresh Calamares install of `ReyOS-Test`, first time this bug class has an actual real-install repro rather than a theory (see the "App launcher shows no per-app icons" entry below, which is related but distinct — that one's about wrong/missing icons, this one is about the taskbar entry not existing at all). ReyOS Browser and Dolphin, opened from the app launcher, render their window on screen correctly but get no Task Manager button. Ruled out so far:
- **Not Wayland-specific**: reproduced identically after explicitly selecting the "Plasma (X11)" SDDM session, not just the default Wayland one.
- **Not a pure first-boot race**: initially looked like one (a relogin made the browser's taskbar entry appear correctly once), but a later same-session close+reopen of the browser reproduced the missing entry again, and a full fresh reboot reproduced it again too. So it's intermittent/recurring, not "broken once at first boot, fixed forever after."
- Separately, one pinned taskbar launcher (likely Dolphin's) shows a **blank/generic icon** instead of its real one — could be the same root cause as the Kickoff icon bug below, or unrelated; not disentangled yet.
- Same session, later report: pinned "favorite" launcher icons in the taskbar not showing at all (not just the wrong icon) — likely the same underlying bug, not confirmed as a separate issue.

First diagnosis attempt via terminal relay (no working SSH to a real install — see the SSH-timeout entry below) hit a dead end: `wmctrl` isn't installed, `journalctl --user -b | grep -i taskmanager` ran but found nothing, and `journalctl --user -u plasma-plasmashell -b` reported no journal files exist at all for that scope.

**Second attempt, same day, got real shell access via QMP keyboard input (typed into Konsole through `virsh qemu-monitor-command --hmp "sendkey ..."`, screenshotting after each command) — found real, concrete evidence:**

- The panel's task widget is `org.kde.plasma.icontasks` (Icons-only Task Manager), not the classic `org.kde.plasma.taskmanager` — a legitimate, common choice, not inherently broken. Confirmed via `~/.config/plasma-org.kde.plasma.desktop-appletsrc`: `[Containments][20][Applets][22]` → `plugin=org.kde.plasma.icontasks`.
- Its `launchers=` config is correctly populated: `applications:systemsettings.desktop,applications:org.kde.discover.desktop,applications:reyos-control-center.desktop,applications:org.kde.dolphin.desktop,applications:reyos-browser.desktop` — five real pinned apps including Dolphin and ReyOS Browser. So the *configuration* is right; whatever's wrong is in how icontasks renders/tracks against that config at runtime.
- Live screenshots taken throughout the session showed the actual visible icon count fluctuating between 3 and 5 for the *same* unchanged config — sometimes showing only 3 (kickoff + 2), sometimes more — with no consistent pattern found tying the count to which apps were actually running.
- `plasmashell` itself is healthy: single stable process (`ps -o pid,etimes,cmd -C plasmashell` showed one process, ~69 min uptime matching session uptime, no crash-restart), and `coredumpctl list` showed no crashes. So this isn't a crash-loop — icontasks is up and rendering *something*, just not consistently reflecting either its own static `launchers=` list or actually-running windows (Konsole, opened live during this diagnosis, never got an entry either, confirmed via direct observation, not just the browser/Dolphin from earlier).
- A dimmed "▾"-style icon visible in the panel might be icontasks' own overflow indicator (shown when there's insufficient width for all icons) — but the panel has substantial unused blank space, so a real width-overflow seems unlikely; not confirmed either way, a mouse click aimed at it (via QMP `mouse_move`, using the 0–32767 absolute-pointer scale, not raw pixels — first click attempt failed silently by sending raw pixel coordinates instead) landed inconclusively.

**Next steps if resumed**: the QMP-keyboard-input + screenshot loop is a real working method now for driving a real install without SSH (see the recipe above) — reuse it rather than re-discovering it. Worth trying: `qdbus6 org.kde.plasmashell /PlasmaShell org.kde.PlasmaShell.evaluateScript` with a script that dumps the task manager's actual model contents (window list icontasks itself sees), and precisely locating/clicking that overflow-style icon to see what it actually reveals.

## Control Center renders without icons/wrong theme if launched while the session is locked

Observed directly (2026-08-18): launching `python3 /usr/share/reyos/control-center/main.py` while the KDE session was still at the lock screen produced a window with the correct layout but a generic light Qt style and no sidebar icons at all. A second launch after the session was fully unlocked and settled rendered correctly (Midnight Copper dark theme, all sidebar icons present). Working theory, not rigorously isolated: Qt/Kirigami's icon-theme and platform-style lookup comes back empty if the app starts before Plasma's theming services are fully live (e.g., right at/before unlock), and it silently falls back instead of retrying. Low priority — no normal user workflow launches Control Center from a locked screen — but worth a real isolated repro if it's ever hit organically (e.g. via an autostart entry that races the lock screen on login).

## Welcome wizard sometimes needs a double-click on first launch

Launched via autostart with no window focus — the first click on any button gets consumed by the compositor just to raise/focus the window, never reaching the button underneath. A retry-based `requestActivate()` loop reduced but did not eliminate it. Leading theory: Wayland's activation-token model blocks self-activation for apps launched via a raw systemd/XDG autostart entry with no token-granting launch path, which would make this a platform limitation rather than something fixable purely in app code. Not revisited since first observed.

## Bottom panel isn't reliably "fit content, centered" out of the box

No stored width/alignment key has ever been found in any panel-building path (the old static `panel-template.conf` never had one, and it's since been established that file is dead code anyway — see `fixes.md`; the two live Plasma-scripting panel builders, `reyos-apply-branding.sh` and `reyos-kde-customization`'s script, don't set one either). A real fix needs someone to set "Fit Content" + centered live via Plasma's own Edit Mode UI, then diff the resulting `plasma-org.kde.plasma.desktop-appletsrc` to find the real keys Plasma writes, and add those to whichever script is the actual source of truth. Deprioritized — adjustable via System Settings in the meantime.

## Custom `reyos-*` packages can't be opt-in installed post-boot (architectural gap)

`[reyos-local]` in `packages.x86_64`'s `pacman.conf` points at `file:///home/reyrubi/reyos-build/local-repo`, a path that only exists on the build VM. Baking a `reyos-*` package into the squashfs at ISO-build time works fine, but any `reyos-*` package meant to be offered as an opt-in install *after* boot (e.g. from Welcome's software picker) has no way to resolve on a standalone booted system. No current package needs this (the `reyos-kernel`/`linux-cachyos` case that originally surfaced this was removed entirely), but it'll resurface the next time a custom package needs to be opt-in rather than pre-baked. Not attempted — would need either shipping a self-contained repo subset on the ISO itself, or generating `pacman.conf` at build time with a path that ships with the image.

## Desktop right-click menu keeps stale/white icons after switching to ReyOS Light

Confirmed live (2026-08-20) on a real fresh install: after switching Look and Feel to ReyOS Light via Control Center (which already restarts `plasmashell` specifically to fix stale icon colors — see `applyLookAndFeel` in `reyos-control-center-gui`'s `main.py`), the desktop's own right-click context menu still shows some icons washed-out/pale against the new light background — "Create New" and "Icons" specifically, both symbolic/monochrome icons that are supposed to auto-tint to the active palette. "Desktop and Wallpaper" (a full-color icon, not palette-tinted) renders correctly in the same menu, and Control Center's own sidebar icons *do* correctly refresh after the theme switch — so this is narrower than the already-fixed bug, not a full regression of it. Working theory, not confirmed: this menu's icons may come from a separate cache/lookup path (built by the desktop `Containment` itself, not something a `plasmashell` process restart touches) that doesn't re-tint on a live theme change. Not yet investigated further — this is on a real installed system with no SSH access (by design), so root-causing it needs either the Dev VM (build a same-theme-switch repro there, where shell access exists) or a live GUI debugging session with VNC/spice-viewer.

Reconfirmed on a second, separate fresh install (2026-08-20 later session), same symptom. New detail from this report: Control Center itself doesn't pick up the theme switch live either — has to be closed and reopened to reflect it (separate from the desktop context-menu icon issue above; Control Center's *sidebar* icons were previously said to refresh fine after the `plasmashell` restart, so this may be Control Center's own window chrome/style, not sidebar icons — needs a live session to tell apart).

## SSH to a real ReyOS-Test install times out (silently dropped, not refused)

Observed 2026-08-21 trying to live-repro the icon bugs below: booted `ReyOS-Test` fresh into its real installed system (not live-boot — SDDM showed a real login prompt, no autologin, matching installed-system behavior). `virsh domifaddr --source agent` confirmed the correct IP, but every SSH attempt (`liveuser`, `reyrubi`) timed out with no response at all — not "connection refused," which would mean sshd isn't listening; a silent timeout is what a default-deny firewall produces. Notable: a live-boot session on this exact same VM earlier the same day could SSH in fine. `ufw` ships in `packages.x86_64` but nothing in `customize_airootfs.sh` enables `ufw.service` by default, so this shouldn't be firewall-caused unless something else turned it on — not confirmed, `virsh send-key`/QMP keyboard input into the console was also unresponsive this session (screenshots updated live, confirming the VM itself was fine, but no typed input ever landed — a known flaky path, see `reyos-vm-gui-automation` notes), so there was no way to get a shell to check `ufw status` directly. Needs revisiting with working console/input access, or SSH retried after confirming from the actual console that the install is fully booted and idle.

## App launcher (Kickoff) shows no per-app icons, only the ReyOS logo

Reported on a fresh install (2026-08-20), not yet reproduced/root-caused. Every entry in the Kickoff application list renders as the ReyOS logo instead of its own icon. Static-code review found the likely gap: nothing in the live boot/branding path ever actually sets `kdeglobals`'s `[Icons] Theme` key — `reyos-apply-branding.sh`'s `apply_visual_identity()` only runs `plasma-apply-colorscheme ReyOS` (colors only) and writes `LookAndFeelPackage` directly (cosmetic/informational key, doesn't apply the package's bundled defaults). The one place that *does* patch an icon-theme default — `reyos-iso/airootfs/root/customize_airootfs.sh`'s sed rewriting `Theme=breeze-dark`→`Theme=ReyOS` inside the look-and-feel packages' bundled `defaults` files — only takes effect if something actually applies that look-and-feel package (e.g. `plasma-apply-lookandfeel`), which nothing in the current boot path calls; `/etc/xdg/kdeglobals` (the other place a system-wide default would live) also has no `[Icons]` section. So today, the live icon theme is whatever Plasma's own compiled-in default is unless Control Center's Appearance page explicitly sets one (`main.py`'s `applyLookAndFeel()` at line ~481, which does write `Icons`/`Theme` and does restart `plasmashell`). The ReyOS icon theme itself (`reyos-icons`, `/usr/share/icons/ReyOS/index.theme`) only ships 4 override icons total and `Inherits=breeze-dark,breeze,hicolor` for everything else — inheritance should cover unbranded apps, so a from-scratch icon-theme bug seems less likely than a stale icon cache (`kbuildsycoca6` / `~/.cache/icon-cache.kcache`) never being rebuilt post-install. Needs a live repro (Dev VM, where shell access exists) to actually confirm which of these it is before touching any code — don't patch blind.

**2026-08-21: checked the Dev VM directly — it will NOT reproduce this.** `kreadconfig6 --file kdeglobals --group Icons --key Theme` on the `ReyOS` Dev VM returns `breeze-dark` (untouched default, matches the "nothing sets [Icons] Theme" theory above), which is a fully populated icon theme — that can't produce an "only the ReyOS logo" symptom regardless of which of the two theories above is right. The Dev VM has been branded/used for weeks and never had its icon theme actually switched to `ReyOS` (no Look-and-Feel switch was ever done there), so it's simply the wrong environment to reproduce a bug that only ever showed up on a *fresh install*. A real repro attempt same day (booting `ReyOS-Test`'s actual installed system) was blocked entirely by VM access problems — see the SSH-timeout entry above and `reyos-vm-gui-automation` for the flaky-input history. **Next attempt needs either working console/SSH access to a fresh install, or reproducing on the Dev VM only after first actually switching its Look and Feel to `org.reyos.desktop` via Control Center** (to put it in the same state a fresh install would be in, if `applyLookAndFeel()` is what sets it).

## Live-boot session sometimes creates zero Plasma panels

Confirmed on 2 of 3 fresh `ReyOS-Test` live boots off the 2026-08-20 ISO (2026-08-20): `qdbus6 org.kde.plasmashell /PlasmaShell org.kde.PlasmaShell.evaluateScript "print(panelIds.length)"` returned `0` minutes after login, with `plasmashell`/`kwin_wayland` both alive and initially consuming real CPU, then settling to near-idle by ~5 minutes uptime — genuinely stalled, not still mid-bootstrap (ruled out the documented "Plasma's first-boot bootstrap races any script" gotcha in `docs/DEVELOPER.md`, since idle CPU at 5+ minutes means nothing is still working on it). Confirmed NOT caused by `reyos-live-wallpaper.sh` (the live-ISO-only wallpaper script) — read its full source, it only writes wallpaper config via `qdbus6`/`kwriteconfig6`, never touches panels, and its own journal output was clean (the "malformed"-looking log lines turned out to just be its own `qdbus6 org.kde.plasmashell` healthcheck listing object paths, not an error). Root cause not yet found. Interestingly, Calamares itself renders fine as its own window regardless of this — so the stall is specific to Plasma's own panel/containment creation, not a general compositor failure. Reproduce again on the Dev VM (where SSH/shell access exists throughout, unlike a real install) with `journalctl -b` captured from second one to isolate what's failing during containment creation.

## Desktop Folder Settings dialog shows a stock "About" tab

Right-click desktop → Configure Desktop and Wallpaper opens Folder View's own settings dialog, which always includes a generic plugin "About" tab appended automatically by Plasma's own config-dialog framework — not specific to ReyOS's config, and no kiosk restriction found to suppress it. Purely cosmetic; disproportionate effort to fix (would mean patching Plasma itself). Deprioritized.
