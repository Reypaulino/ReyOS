> **2026-09-09/10 (latest) — the long-standing pacman.conf/reyos-local bug is finally found and fixed for real, CachyOS removed entirely, and the publish workflow changes going forward.** Root cause (never found in any prior session): `profiledef.sh`'s `pacman_conf` only controls which repos `mkarchiso` installs packages *from* during the build — it was never copied into the shipped image's own `/etc/pacman.conf` (no `airootfs/etc/pacman.conf` overlay existed). Fixed by adding that overlay file. That surfaced a second, deeper bug: `/etc/pacman.d/gnupg` is tmpfs-mounted and reset every boot; `pacman-init.service` re-ran `pacman-key --populate` (standard Arch keyrings only) but never re-trusted the ReyOS signing key, so every real install failed `key ... could not be looked up remotely` on first package operation. Fixed by adding `pacman-key --add`/`--lsign-key` to that same service. **Verified end-to-end on a genuinely fresh Calamares install** (erase disk → real install → reboot → first login → Welcome's software picker installing `btop`) with zero manual steps.

## Performance tooling — built 2026-08-20, live-verified 2026-08-21

Built the same day as the Welcome/panel fixes below. **Live-verified 2026-08-21**: booted the v6 ISO on `ReyOS-Test` (live session, cdrom attached alongside the existing installed disk rather than a fresh reinstall) — desktop and Calamares came up clean, and over SSH: `zramctl` showed `/dev/zram0` active as a 1.9G zstd swap device, `systemctl is-active systemd-oomd` → active, `systemctl is-active reyos-preloadd` → active with a clean startup line in its journal. `systemctl --failed` showed one unrelated pre-existing unit (`systemd-loop@...sr0.service`, an artifact of this test's non-standard dual-disk+cdrom setup, not caused by any of the three changes below) — no regression from zram/oomd/preloadd.

- [x] **zram** — `zram-generator` added to `packages.x86_64`, config at `reyos-base/files/etc/systemd/zram-generator.conf` (zstd, `min(ram/2, 4096)` size, swap-priority 100). `reyos-base` pkgrel 3→4.
- [x] **systemd-oomd** — `systemctl enable systemd-oomd.service` added to `customize_airootfs.sh` alongside NetworkManager/sddm. Default config left untouched (already sane for desktop use).
- [x] **`reyos-preloadd`** — new `reyos-preload` package, the "full adaptive version" the user explicitly asked for over a static-list alternative. Real `preload` was ruled out (AUR-only, no AUR helper shipped, largely unmaintained, mostly benefits mechanical drives). Design: a Python daemon scans `/proc/*/maps` every 10s, and on any *new* process launch looks up that executable's historical file working set (persisted to `/var/lib/reyos-preload/state.json`) and `posix_fadvise(WILLNEED)`s the files it's confident about (seen in ≥60% of past launches, ≥3 launches tracked) — a co-occurrence/per-executable model, deliberately scoped down from full continuous-time Markov chains for one-session buildability. Only runs the actual prefetch when load average and memory-available both pass safety thresholds; never issues `DONTNEED` (never evicts), so a wrong prediction can waste idle IO but can't make anything worse. Systemd unit runs at `Nice=19`/`IOSchedulingClass=idle`/`MemoryMax=64M`.
- Two new bugs found on a second fresh install the same evening (unrelated to the above, found while re-verifying): Kickoff app launcher shows no per-app icons (only the ReyOS logo), and Control Center/desktop right-click menu icons don't refresh live on a theme switch (Control Center needs a manual close+reopen). Logged in `bugs.md` with a static-review diagnosis (likely `[Icons] Theme` never actually gets applied live, plus a possible stale icon cache) — not fixed blind, needs a live VM repro first.

## Ubuntu/Debian .deb packaging for reyos-browser (found undocumented, fixed a real bug 2026-08-24)

A `.deb` for `reyos-browser` already existed (built by an earlier session, never logged in this repo's docs) but was **broken on a genuinely clean system**: `Depends:` only listed `python3, kdialog, libnotify-bin`, missing the entire QtWebEngine/Chromium runtime library set. Confirmed via a real install test in a fresh, unmodified `ubuntu:24.04` Docker container (chosen specifically to avoid any library already present from other apps on the dev host masking the gap) — `apt install ./reyos-browser_0.1.0-83ubuntu1_amd64.deb` succeeded, but launching immediately hit `ImportError: libnspr4.so: cannot open shared object file`, then after installing that, `libnss3.so`, then a Qt platform-plugin failure needing `libxcb-cursor0`.

**Fixed**: rebuilt at `/home/reyrubi/reyos-browser-deb` with a corrected `Depends:` line (added `libnspr4, libnss3, libxcb-cursor0, libatk1.0-0t64, libatk-bridge2.0-0t64, libcups2t64, libdrm2, libgbm1, libxcomposite1, libxdamage1, libxfixes3, libxrandr2, libxkbcommon0, libasound2t64, libpango-1.0-0, libcairo2, libxss1, libxtst6, fonts-liberation` — the standard QtWebEngine/Chromium runtime set, cross-checked against `ldd` on the actual bundled `QtWebEngineProcess` binary), bumped to `0.1.0-84ubuntu1`. **Re-verified in a second fresh container**: plain `apt install` now resolves every dependency automatically, and the app launches cleanly as a non-root user with the full expected process tree (main process + zygote + renderer) and no missing-library errors.

Published as a GitHub Release on `Reypaulino/ReyOS` (`reyos-browser-v0.1.0-84ubuntu1`; the broken `83ubuntu1` release was deleted rather than left up) and linked from the website's Ubuntu/Debian download section.

**Real gap this exposes**: the Debian packaging (`DEBIAN/control`, staging tree at `~/reyos-browser-deb`) lives entirely outside git — unlike the Arch `PKGBUILD` or the new Flatpak manifest, there's no version-controlled source of truth for it. Worth bringing into the repo properly (e.g. a `debian/` dir under `reyos-packages/reyos-browser/`) before the next rebuild, so this exact bug class doesn't silently reappear from an untracked, unreviewed staging directory.

## reyapps.com website
- [ ] **"Build ReyOS Reader" section for Ubuntu**, matching the existing "Build ReyOS Browser" section. **2026-09-10 update — the previous plan here was wrong on two counts, both confirmed by actually testing, not theorizing:**
  1. Ubuntu 24.04 does **not** ship a Qt6/KF6 Kirigami at all — `qml6-module-org-kde-kirigami` doesn't exist. The only Kirigami package in Ubuntu's repos is `qml-module-org-kde-kirigami2` (Kirigami **2**, built against **Qt5** — `libqt5core5t64` etc.), incompatible with PySide6's Qt6 runtime. Checked directly with `apt-cache search`/`apt-cache show` on a real Ubuntu 24.04 host.
  2. Tried the fallback of Flatpak (`org.kde.Platform//6.9`, which does bundle a real Qt6 Kirigami) with pip-installed PySide6 bundled the normal way. Built fine, but **crashed at runtime**: `Cannot load library .../libKirigamiPrimitivesplugin.so: undefined symbol: _ZNK11QQmlPrivate18AOTCompiledContext9setLocalsE...`. Root cause: pip's PySide6 wheel bundles its own private Qt 6.9.2 build, which is not ABI-compatible with the KDE runtime's separately-built Qt 6.9 that Kirigami's plugins link against, even though both call themselves "6.9". Not fixable via QML2_IMPORT_PATH — confirmed by actually pointing it at the runtime's Kirigami and watching it fail to load. A real fix would mean compiling PySide6 from source against the runtime's own Qt (multi-hour build, own risk) — not attempted.
  - **Decided path (user, 2026-09-10): drop the Kirigami dependency from Reader entirely** — rewrite `Main.qml`'s `Kirigami.ApplicationWindow`/`GlobalDrawer`/`PageRow` navigation onto plain `QtQuick.Controls`, the same way `reyos-browser` is built with zero KDE Frameworks dependency.
  - **Done, 2026-09-10**: every `org.kde.kirigami` import removed from all 8 QML files, replaced by a new `qml/kirishim/` compat layer (Units/Theme/Heading/Icon/Separator/PlaceholderMessage/SearchField/AbstractCard/Page/ScrollablePage/OverlaySheet/Action/GlobalDrawer/ApplicationWindow) built on plain QtQuick Controls — see `fixes.md` for the three real bugs the rewrite exposed (window defaulting invisible, a circular width binding collapsing the sidebar to 0, `StackView.initialItem` never firing) and how each was found/fixed via live `QQmlProperty` inspection, not guesswork. Verified end-to-end on this Ubuntu host: Library, PDF Tools, and a real opened PDF all render correctly with real icons and no QML errors.
