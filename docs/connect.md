# ReyOS Connect

A native ReyOS front-end for KDE Connect. Does not reimplement KDE Connect's protocol, pairing, encryption, or transport — `kdeconnectd` (the real KDE Connect daemon) is the backend; ReyOS Connect is a Kirigami/QML GUI that talks to it over D-Bus and presents a simpler, ReyOS-branded device dashboard.

```
iPhone → KDE Connect iOS (official app) → encrypted KDE Connect link → kdeconnectd (ReyOS) → ReyOS Connect GUI
```

- Package / binary: `reyos-connect`
- Application ID / desktop file / icon name: `org.reyos.Connect` (explicit deviation from the plain `reyos-<name>` convention used by Reader/Browser/Control Center — this app's brief asked for reverse-DNS naming specifically, kept as-is rather than "corrected" to match the others)

## Phase 0 audit findings (2026-08-31)

1. **`AGENTS.md`** read — no prior KDE Connect work anywhere in this repo (`grep -ril kdeconnect .` returned nothing before this session).
2. **KDE Connect was not installed anywhere in ReyOS** — absent from `reyos-iso/packages.x86_64` and every `reyos-packages/*/PKGBUILD`. Installed fresh on the Dev VM for this audit: `kdeconnect 26.08.0-1.1` (pulls in `kcontacts`, `kpeople`, `libfakekey`, `qt6-connectivity`).
3. **Reusable app shape**: `reyos-reader` (a from-scratch standalone PySide6/QML app, not a Control Center page) is the closest template — `/usr/bin/<name>` launcher script, `main.py` bootstrapping `QGuiApplication`/`QQmlApplicationEngine` with a `Backend(QObject)` context property, `QThread` workers (`ActionWorker`/`ListWorker` pattern from `control-center-gui`) for anything blocking, Kirigami `ApplicationWindow`. ReyOS Dark/Light theming comes for free through Kirigami reading the active Plasma color scheme — no per-app theme switch needed, confirmed by every existing app.
4. **`python3 -c "from PySide6 import QtDBus"` succeeds** on the Dev VM — PySide6's Qt D-Bus bindings are available with no extra dependency. Used directly (native Qt event-loop-integrated D-Bus signal delivery) instead of shelling out to `qdbus6`/`kdeconnect-cli`, so device/pairing state updates arrive as real signals, not polling.
5. **D-Bus interfaces verified against the actual installed `kdeconnectd` (26.08.0)** two ways: (a) live introspection of the daemon's real running object (`qdbus6 org.kde.kdeconnect.daemon /modules/kdeconnect`) and (b) fetching the exact `v26.08.0`-tagged upstream source for the per-device and per-plugin classes, then cross-checking the fetched method/property names against `strings` output of the installed `libkdeconnectcore.so.26.08.0` (e.g. `supportedPlugins`, `isPairRequestedByPeer`, `statusIconName` all present in the real binary). No interface below was guessed.

### Daemon interface — `org.kde.kdeconnect.daemon` at `/modules/kdeconnect`
(confirmed via live introspection)

- Methods: `devices()` / `devices(onlyReachable)` / `devices(onlyReachable, onlyPaired)`, `deviceNames(...)` (same overloads), `deviceIdByName(name)`, `selfId()`, `announcedName()`, `setAnnouncedName(name)`, `forceOnNetworkChange()`, `sendSimpleNotification(...)`
- Signals: `deviceAdded(id)`, `deviceRemoved(id)`, `deviceListChanged()`, `deviceVisibilityChanged(id, isVisible)`, `pairingRequestsChanged()`
- This is the top-level "what devices exist / became visible" feed — ReyOS Connect's device list is driven entirely by these signals, no polling.

### Per-device interface — `org.kde.kdeconnect.device` at `/modules/kdeconnect/devices/<id>`
(confirmed via `v26.08.0` source, cross-checked against the installed `.so`)

- Properties: `name`, `type`, `iconName`, `statusIconName`, `isReachable`, `reachableAddresses`, `isPaired`, `isPairRequested`, `isPairRequestedByPeer`, `pairState`, `verificationKey`, `supportedPlugins`
- Methods: `loadedPlugins()`, `hasPlugin(name)`, `requestPairing()`, `acceptPairing()`, `cancelPairing()`, `unpair()`, `isPaired()`, `isReachable` (via property), `pluginIconName(name)`
- Signals: `pairStateChanged(int)`, `pairingFailed(error)`, `reachableChanged(reachable)`, `nameChanged(name)`, `pluginsChanged()`, `linksChanged()`
- **State mapping used by ReyOS Connect** (spec requires distinguishing these, not inferring Connected from a stale paired flag): `isPaired == false` → *Available* (if reachable) or not shown; `isPairRequested == true` → *Pairing (outgoing)*; `isPairRequestedByPeer == true` → *Pairing (incoming, needs Accept/Reject)*; `isPaired && isReachable` → *Connected*; `isPaired && !isReachable` → *Paired, Disconnected*. "Unreachable" (paired, was connected, link just dropped) is the transition caught live by `reachableChanged(false)`.
- `loadedPlugins()` is what actually gates the UI, not `supportedPlugins` — it reflects the plugins *negotiated as active for this specific remote device*, which is what makes capability detection correct for iOS (no `mousepad`/`remotecontrol` etc. show up as loaded for an iPhone even though the desktop side supports them).

`runcommand` (the plugin behind "Remote Commands"): **has no D-Bus methods at all** in this version — confirmed from source. Commands are pre-configured entirely locally as a JSON blob (`{"key": {"command": "..."}}`) under that plugin's own `KdeConnectPluginConfig`, and `kdeconnectd` only ever executes a command whose key the phone names — it can never send an arbitrary command string. This is exactly the safety model the spec requires ("never construct arbitrary shell commands from untrusted phone input"), already enforced by KDE Connect itself. ReyOS Connect's Commands page edits that same local config (a small JSON-in-KConfig editor: add/remove/rename entries), it does not add any new execution path. Exact on-disk config path confirmed at implementation/test time (per-device config directory under `~/.config/kdeconnect/`).

### Connect by IP address

The KDE Connect iOS app supports adding a device by IP address directly (useful when broadcast discovery can't reach it -- different subnet, VPN, hotspot). This maps to a real daemon feature, not something invented for ReyOS Connect: `org.kde.kdeconnect.daemon`'s `customDevices` `readwrite` `QStringList` property. Confirmed from `v26.08.0` source (`Daemon::setCustomDevices()`, `LanLinkProvider::getBroadcastAddresses()`): each entry is a bare IP/hostname (`QHostAddress(entry)`, no port, no scheme), and setting the property sends a direct (non-broadcast) identity probe to that address in addition to the normal LAN broadcast. ReyOS Connect exposes this as "Connect by IP Address" in the troubleshooting card on the main dashboard: add/remove entries, each change re-triggers `forceOnNetworkChange()`.

**A real PySide6/QtDBus marshalling bug found and fixed while building this**: setting `customDevices` to an **empty** list via `QDBusVariant(python_list)` failed live with `org.qtproject.QtDBus.Error.InternalError` ("Internal error") -- reproduced in isolation and confirmed this is a *client-side* Qt binding limitation (an empty python list gives Qt no element to infer the D-Bus `as` signature from), not a kdeconnectd bug; the daemon never even received a malformed request. Fixed by building an explicitly-typed empty `QStringList` via `QDBusArgument.beginArray(QMetaType.Type.QString)`/`endArray()` only for the empty case (the non-empty case already marshals fine as a plain list). A separate attempt at appending elements into a `QDBusArgument` array via `arg << value` produced a malformed message and aborted the local D-Bus client process outright (`dbus: Writing an element of type array, but the expected type here is string`) -- confirmed this never reached/affected `kdeconnectd` itself (same daemon PID before and after), but it's why the fix uses plain-list marshalling for every non-empty case and only touches `QDBusArgument` for the empty-list edge case specifically, rather than building every list through it.

### Firewall

The real port range, from KDE Connect's own shipped `/etc/ufw/applications.d/kdeconnect` profile (not guessed): **1714:1764, both TCP and UDP**. ReyOS Control Center's Firewall page already has a NOPASSWD sudoers rule (`/etc/sudoers.d/99-reyos-system-menu`, installed by Calamares at first boot) covering `ufw status *` and `ufw allow *` — so `sudo ufw allow KDEConnect` (the app-profile name) and `sudo ufw status` both already work with **no new sudoers rule needed**. ReyOS Connect's "Check Connection" diagnostic reads `ufw status` to report whether the range is open; opening it (if closed) reuses this existing rule and still shows a confirm dialog before running, matching the Firewall page's own UX. Never auto-disables the firewall or opens unrelated ports.

### Packaging

`kdeconnect` is a hard `depends=` of the `reyos-connect` PKGBUILD, not an ISO base-package addition and not a runtime "install for me" button — this makes "KDE Connect missing" impossible for anyone who installs `reyos-connect` via pacman (the only way v1 needs to handle "backend missing" is the software-not-yet-installed case, which pacman itself prevents, plus the "installed but daemon not running" case, which is a real runtime state ReyOS Connect does detect and explain).

**Added to `reyos-iso/packages.x86_64` (2026-09-02)**, after this session's real device testing (Bluetooth/Battery/VPN/Remote-Control all proven against real hardware and a real iPhone — see the Part 3 and Remote Desktop sections above). `krdp` was added alongside it explicitly, since it's only an `optdepends=` of the PKGBUILD and wouldn't be pulled onto the ISO automatically otherwise. One known gap at ship time: Remote Desktop's video/input path is real, working code (login + RDP handshake proven against a real krdp server) but has **not** been screenshot-verified end-to-end on real hardware — the only environment available this session to test it (the Dev VM) has no GPU acceleration, and the physical host's own QEMU install turned out to have a broken virtio-gpu-gl module, blocking a fix. Not yet added to ReyOS Welcome's app picker.

## A real, unexpected finding: `kdeconnectd` self-heals via D-Bus activation

`/usr/share/dbus-1/services/org.kde.kdeconnect.service` ships with the `kdeconnect` package and registers standard D-Bus service activation for `org.kde.kdeconnect`. Confirmed live: killing `kdeconnectd` (`pkill -x kdeconnectd`) and then simply constructing a `QDBusInterface` against it (which `KdeConnectWatcher.__init__` does on every ReyOS Connect launch) causes the session bus to **respawn it automatically within about a second**, before ReyOS Connect's own "not running" placeholder ever gets a chance to render. This makes a crashed daemon effectively self-healing in practice — good for reliability, but it means the "KDE Connect isn't running / Start KDE Connect" placeholder path is real, correctly implemented, and defensively worth keeping (it still covers the moment right at startup, and systems where activation is disabled), but is rarely the thing a user will actually see.

## More real bugs found and fixed during testing

- **`customDevices` empty-list marshalling** (PySide6/QtDBus client-side bug): see "Connect by IP address" above.
- **Device list not refreshing after a pairing action**: see below.

`Backend`'s pairing/unpair Slots (`acceptPairing`, `rejectPairing`, `requestPairing`, `unpairDevice`) only emitted `actionFinished` on completion, relying on `kdeconnectd`'s own `pairStateChanged` D-Bus signal to trigger a device-list refresh. Confirmed live: after a real, successful `acceptPairing()` call (banner correctly read "Device paired."), the device card kept showing the pre-action "Wants to pair" UI because no fresh signal happened to arrive in time to trigger a re-fetch. Fixed by having `Backend._run()` also emit `devicesChanged` once any action finishes, so the UI always re-syncs from a fresh `Properties.Get` round trip immediately after a user-initiated action, independent of whether the daemon's own change signal shows up.

## Known limitations (v1)

- `sftp` (browsing the phone's remote filesystem) is out of scope for v1 — only push-based Send File / receive-into-Downloads.
- QR pairing: KDE Connect's own desktop-side pairing flow is trust-on-first-use over the existing encrypted link, not QR-code-based on this version — no `[Pair with QR Code]` button in v1 (documented as deferred per the spec's own instruction, not invented).
- Internet/VPN remote access is explicitly out of scope for v1 per the spec.

## v2 — Provider architecture, VPN remote access, remote control, Bluetooth (2026-09-01)

v2 extends ReyOS Connect from a single-transport (LAN/KDE Connect) dashboard into a device-connectivity app spanning three transports: LAN/Wi-Fi (KDE Connect, unchanged from v1), VPN (remote reachability), and Bluetooth (BlueZ, iPhone-specific integration where actually supported). This section documents the architecture and the real findings behind it; see the per-part sections below for testing status.

### Capability model

The GUI does not know which backend provides a capability — it renders a fixed capability→state map, and providers populate it. A capability is one of: `files`, `clipboard`, `send_link`, `remote_input`, `remote_desktop`, `ssh`, `battery`, `contacts`, `calls`, `messages`, `vpn`, `bluetooth`. Each reports one of: `AVAILABLE`, `UNAVAILABLE`, `NOT_TESTED`, `ERROR`. Defined in `providers/capability.py` as plain string constants (not a Python enum crossing into QML) to match the rest of this codebase's convention of plain dict/string state fields (`device_snapshot()`'s `state` field, etc.) — `Kdc`'s KDE Connect layer, `vpn_provider.py`, `bluetooth_provider.py`, and `remote_provider.py` each populate a subset of this map; nothing is faked to `AVAILABLE` without a real, current detection behind it, and phone-side capabilities (contacts/calls/messages) stay `NOT_TESTED` until exercised against a real paired iPhone specifically (not inferred from BlueZ UUID advertisement alone).

### Phase 0 audit findings (2026-09-01)

1. **Tailscale, not WireGuard, is the user's real VPN.** The physical host (not a ReyOS VM — the user's own daily-driver Ubuntu box that also hosts the ReyOS/libvirt VMs) already runs `tailscale` with a live tailnet: this host (`rey-paulino`, `100.82.152.48`), a Raspberry Pi 5 (`raspi5`, `100.70.115.97`, active, offers exit node), and an iPhone (`iphone-13`, `100.104.219.46`, offline at audit time, last seen 6 days prior). No `wg` binary exists on the host at all — WireGuard is not in use there. `reyos-connect` itself only ever runs on a ReyOS VM/install, never on this host directly, so Tailscale is a bring-your-own backend from ReyOS's point of view exactly like WireGuard already is — detected if installed, never auto-installed, never auto-logged-in.
2. **ReyOS Control Center already has two separate, non-overlapping WireGuard implementations** — a pre-existing duplication, not something introduced here, left as-is (out of scope to consolidate for this feature):
   - `VpnPage.qml` (Control Center's "VPN" nav item) → `Backend._compute_vpn_status()`/`connectVpn()`/`disconnectVpn()` in `control-center/main.py` (~line 1339) → raw `/etc/wireguard/*.conf` + `wg-quick@<name>.service` systemd units + `sudo wg show interfaces`.
   - `NetworkPage.qml` (buried inside the "Network" page) → `refreshWireguardStatus()`/`importWireguardConfig()` (~line 1966) → NetworkManager via `nmcli connection ... type wireguard` (no sudo needed — NM's own polkit rules cover the session user).
   ReyOS Connect's `vpn_provider.py` detects **both** mechanisms and merges them into one WireGuard status view (an interface is "active" if either reports it active) rather than picking one as canonical, since a real user's system could have either in play.
3. **Real backends confirmed present on the Dev VM**: `wg`/`wg-quick` (wireguard-tools), `nmcli` 1.58.1, `bluetoothctl`/`bluez` 5.87 + `bluez-utils` 5.87 (both already in `reyos-iso/packages.x86_64`, `bluez` pulled in as `bluez-utils`'s dependency). `sshd` is enabled+active on the Dev VM specifically for the dev workflow (see [[reyos-dev-vm-access]]/`docs/DEVELOPER.md`) — **not** representative of a real install, where `sshd` is not enabled by default (confirmed in `reyos-vm-gui-automation` memory / prior sessions: "No SSH on real ReyOS installs, by design"). At audit time, no `krdp`, `xrdp`, or any VNC/RDP *server* was found anywhere on the Dev VM (`bvnc` is KDE's VNC *client*, not a server) — Remote Desktop correctly detected as unavailable. **Update, 2026-09-02**: `krdp` (part of Plasma 6 itself, official `extra` repo) was installed and wired up for real — see the Part 2 "Remote Desktop" section below for the full findings.
4. **No Bluetooth adapter is passed through to the Dev VM** (`bluetoothctl show` returns nothing, `org.bluez` isn't even registered on the session/system bus). Bluetooth development and testing for this feature happens on the physical host instead (real adapter, real `bluetoothd`), same pattern as the "real host is a legitimate second test target" note in [[reyos-dev-vm-access]] — Bluetooth *UI/detection logic* is still shipped as part of the `reyos-connect` package meant for real ReyOS installs, just verified against the host's real BlueZ stack since the Dev VM structurally cannot exercise it.
5. **No iPhone is actually Bluetooth-paired anywhere** at the time this was built (confirmed by checking both the Dev VM — no adapter at all — and the host's paired-device list, which has an Xbox controller and one other Bluetooth HID game controller, no phone). The "iPhone already pairs over Bluetooth" premise in the original ask referred to the same-session KDE Connect LAN pairing (see the v1 sections above), not a real Bluetooth pairing — confirmed directly with the user rather than assumed. Every Bluetooth phone-capability item (contacts/calls/messages) therefore stays `NOT_TESTED — REAL IPHONE REQUIRED`, and the Bluetooth provider itself is built against whatever *is* actually paired on the host (the Xbox controller, the HID device) to prove the detection code is real and not mocked, pending a genuine iPhone Bluetooth pairing.

   **Update, 2026-09-02**: this genuine pairing happened this session — see "Part 3 real-device results" below for the full findings. Short version: Contacts/Calls/Messages are all real-tested `UNAVAILABLE` (an iOS/MFi-accessory restriction, not a ReyOS gap); Battery is real and `AVAILABLE`.
6. **KDE Connect's `runcommand` plugin config format**, needed for the new safe "Remote Commands" registry (`docs` below): confirmed both empirically (real per-device config dir exists at `~/.config/kdeconnect/<device_id>/kdeconnect_runcommand/config` on the Dev VM once a device is paired) and from the `v26.08.0` source (`KdeConnectPluginConfig::getString("commands", "{}")`, a JSON object of `{"<id>": {"name": ..., "command": ...}}` keyed by arbitrary string IDs, no UUID scheme enforced) — written via PySide6's own `QSettings(path, QSettings.Format.IniFormat)` (matches Qt's own on-disk serialization used by `KdeConnectPluginConfig`, which is itself `QSettings`-backed) rather than hand-rolling this app's own INI escaping, avoiding a guessed-format bug.

### Part 1 — VPN Remote Access

`providers/vpn_provider.py`:
- `tailscale_status()` — parses `tailscale status --json` (structured, never scraped text), reports installed/running/authenticated/connected/self Tailscale IP/peers (name, IP, online) — including the iPhone's own tailnet entry (`iphone-13`) once it comes back online, which becomes the "reachable" check for remote access without needing a fresh scan.
- `wireguard_status()` — merges the two Control Center mechanisms described above into one interface list (`name`, `active`, `source: wg-quick|networkmanager`, local IP where available).
- `detect_backends()` — which of the two are installed, for the Tailscale/WireGuard radio choice in "Remote Access".
- Connect/disconnect for Tailscale (`sudo tailscale up`/`down`) is only ever offered when `tailscale status --json` already reports the node as logged-in/authenticated — ReyOS Connect never calls `tailscale login` and never triggers a browser auth flow itself, per the spec's "do not automatically log users into Tailscale."
- "VPN Settings" opens ReyOS Control Center directly (`/usr/share/reyos/control-center/main.py`, the real launcher — there's no `reyos-control-center` binary, confirmed via its `.desktop` file's `Exec=` line) rather than re-implementing config import/profile management a second time.
- **Test Remote Connection** runs, in order: VPN active → private VPN interface/address exists → peer (iPhone) reachable, via the Tailscale peer's own reported online state, falling back to a bounded `ping` if a peer IP is known and reachable by neither → KDE Connect reachable over that address (adds it as a KDE Connect custom device — the same `customDevices` mechanism v1 already built for cross-subnet discovery — and checks for a resulting device/reachability state) → SSH reachability (bounded TCP connect to `:22`) only if `sshd` is confirmed enabled. Every check reports `PASS`/`FAIL` from a real attempt made at click time, never inferred.
- No public exposure: nothing in `vpn_provider.py` or its QML ever touches `ufw`/port-forwarding/UPnP/router config — the only firewall interaction anywhere in ReyOS Connect remains v1's existing KDE-Connect-LAN-ports allowance.

### Part 2 — Remote Control

`providers/remote_provider.py`:
- **Remote Input** — unchanged from v1 (`kdeconnect_remotekeyboard`), now also surfaced from the VPN "Remote Access" test results when reachable over VPN, not just LAN.
- **Remote Commands** — a fixed, ReyOS-curated registry (`Lock ReyOS`, `Open Browser`, `Open Reader`, `Open Control Center`, `Take Screenshot`, `Mute Audio`, `Pause Media`), each mapped to one real, fixed local command (`loginctl lock-session`; `reyos-browser`; `reyos-reader`; `/usr/share/reyos/control-center/main.py`; `spectacle -b -n`; `pactl set-sink-mute @DEFAULT_SINK@ toggle`; a small fixed D-Bus loop over any running `org.mpris.MediaPlayer2.*` player's `PlayPause`, chosen over adding a `playerctl` dependency). The UI lets the user opt individual entries into the phone's KDE Connect Run Commands menu (writes only the enabled subset into that device's `kdeconnect_runcommand` config, per the format above) — there is no free-text command field anywhere in ReyOS Connect, satisfying "do not allow arbitrary shell command input by default" structurally, not just by convention.
- **Remote Desktop** — real backend wired up 2026-09-02: `krdp` (package `krdp`, part of Plasma 6 proper in the official `extra` repo, not third-party) provides `/usr/bin/krdpserver`, a Wayland-native RDP server built on the standard XDG `org.freedesktop.portal.RemoteDesktop`/`ScreenCast` portals (confirmed from the binary's own symbols: `KRdp::PortalSession`, `zkde_screencast_unstable_v1`) — exactly the "maintained upstream component" / "Wayland-compatible remote desktop solution" the spec asks for, nothing reimplemented. Its real systemd `--user` unit is `app-org.kde.krdpserver.service` (confirmed live after installing the package — the `remote_desktop_status()` code had been carrying an unverified guessed unit name, `"krdp"`, since the earlier pass when no backend was installed to check against; corrected now that one is). KDE's own shipped preset (`00-krdp.preset`) explicitly disables it by default ("This service should never be enabled by default, irrespective of distro policy") — confirmed live (`systemctl --user is-enabled` → `disabled`) — ReyOS Connect never overrides that, satisfying "disabled by default" for free rather than having to enforce it itself. Credentials are handled entirely by KDE's own System Settings module (`kcm_krdpserver`, KWallet/QtKeychain-backed — confirmed via the binary's `QKeychain::ReadPasswordJob` symbols and its own "No users configured for login... configure users using kcm_krdp" runtime error) — ReyOS Connect adds "Remote Desktop Settings" (opens the real `systemsettings kcm_krdpserver` page, the exact `Exec=` line from the real `.desktop` file) and "Start/Stop Session" buttons (`systemctl --user start/stop`), and never stores or reads a password itself.
  **A real bug found and fixed by actually running this against the Dev VM's real krdpserver** (not inferred from the unit file): `systemctl --user start` returns success the instant `krdpserver`'s `exec()` call succeeds (`Type=exec` in the unit) — with no username/password configured yet, the real process starts, logs "No users configured for login...", and exits (status 255) well under a second later. `start_remote_desktop()`'s first version only checked that initial `systemctl` exit code and would have reported this as a success — caught live (a follow-up `is-active` check right after showed `active` briefly true, then `failed` moments later) and fixed by re-checking `is-active` after a short settle delay and surfacing the real journal line as the failure detail when it already died.
- **SSH Remote Terminal** — status-only (`systemctl is-enabled`/`is-active sshd`, no sudo needed for a status query). ReyOS Connect never enables `sshd` itself; "Configure" opens Control Center's existing Firewall/network pages. Real installs ship with `sshd` disabled by default (only the Dev VM and live ISO sessions enable it, for the dev workflow itself) — this page will correctly show "Disabled" on a real install unless the user has turned it on.

### Part 3 — Bluetooth / iPhone integration

`providers/bluetooth_provider.py`, pure D-Bus against `org.bluez` (no `bluetoothctl` shelling — Control Center's existing `_bt()` helper works around `bluetoothctl` hanging indefinitely with no adapter by wrapping every call in `timeout`; going straight to D-Bus sidesteps that class of hang entirely and gets real `PropertiesChanged`/`InterfacesAdded`/`InterfacesRemoved` signals instead of polling):
- Adapter + paired-device enumeration via `org.freedesktop.DBus.ObjectManager` at `/` (no hardcoded `hci0` assumption).
- Per-device UUID→profile mapping (HFP/HSP → `calls`, PBAP → `contacts`, MAP → `messages`, A2DP → audio) reports a capability as `AVAILABLE` only in the sense of "this profile is advertised" — actually exercising it (a real contact fetched, a real call answered, a real SMS sent) is what flips it out of `NOT_TESTED`, per the spec's explicit "do not mark PASS based on API existence alone."
- No Apple ID handling anywhere, no iMessage, no reverse-engineered auth — out of scope by the spec's own explicit prohibition, not merely unimplemented.
- **Identity merge**: a KDE Connect device and a BlueZ device are never auto-merged on a name-similarity guess. A small local mapping (`~/.config/reyos-connect/linked-devices.json`) records an explicit user-initiated "Link this Bluetooth device" action; only a manually-linked pair renders as one unified device card (Wi-Fi/Bluetooth/VPN rows + merged capability list, per the spec's "Reynaldo's iPhone" example). Until something is linked, BlueZ devices show on their own separate "Bluetooth" page — this is deliberate per the spec's "if identity matching is uncertain, do not automatically merge incorrectly."

### Part 3 real-device results (2026-09-02) — a real iPhone was Bluetooth-paired and tested

The user's iPhone ("Reyrubi Iphone", `AC:45:00:3D:8A:4E`) was paired for real to the physical host's real BlueZ adapter (`rey-paulino`, `BC:A8:A6:97:F1:7F`) this session — confirmed via `bluetoothctl info`: `Paired: yes`, `Bonded: yes`, `Connected: yes`. **Battery** came through immediately and for free via BlueZ's own `Battery1` D-Bus interface (`Battery Percentage: 60`) — no extra plumbing needed, this capability is genuinely `AVAILABLE`. The iPhone advertises PBAP (`0000112f`), MAP (`00001132`), and both Handsfree UUIDs (`0000111e`/`0000111f`) in its `UUIDs` property, which is exactly why the spec insists advertised UUIDs alone can't be trusted — none of the three actually work end to end:

**Contacts (PBAP)** — real test performed (`bluetooth_provider.probe_contacts()`, wraps the same D-Bus calls validated live via a throwaway `dbus-python` script against `org.bluez.obex`): `CreateSession(dest, {"Target": "PBAP"})` succeeds, `Select("int", "pb")` succeeds, but `GetSize()` returns `0` and **no consent prompt ever appears on the phone**. Conclusion: `UNAVAILABLE`, not `NOT_TESTED` — this was actually run, not inferred. Real cause (well-documented iOS behavior, not a ReyOS bug): full PBAP phonebook sync is only granted to devices iOS recognizes as MFi-certified car-kit accessories; a generic BlueZ/Linux pairing never gets the "Sync Contacts" consent dialog that would unlock this, regardless of profile support.

**Messages (MAP)** — real test performed (`probe_messages()`): `CreateSession(dest, {"Target": "MAP"})` fails outright with `org.bluez.obex.Error.Failed: OBEX Connect failed with 0x43` (OBEX **Forbidden**). Conclusion: `UNAVAILABLE`, real result — iOS refuses the MAP connection at the protocol level for this pairing, same MFi-accessory restriction as PBAP, one step more restrictive (doesn't even let the session open).

**Calls (HFP)** — the deepest real investigation of the three, because exercising actual call-control (ring indication, answer, hang up) needs a real AT-command channel, which BlueZ itself doesn't expose (BlueZ/PipeWire only do SCO *audio* routing) — that needs `oFono`. `oFono` is **not** a `reyos-connect` dependency and was only temporarily installed on the host for this one investigation, then fully removed afterward (`apt purge ofono`, config reverted) — adding a permanent second telephony daemon for a capability that turned out non-functional would violate the "no duplicate daemon without a proven need" rule. What was found, in order:
1. `oFono`'s `RegisterProfile()` for the Handsfree UUID (`0000111e`) failed with `org.bluez.Error.NotPermitted, UUID already registered` — PipeWire's WirePlumber (`bluez5.hfphsp-backend = native`, the ReyOS/Linux-desktop default) already owns that BlueZ profile role for audio, so oFono can never get it without WirePlumber yielding first.
2. A **standard, supported** WirePlumber override (`bluez5.hfphsp-backend = ofono` in a `~/.config/wireplumber/bluetooth.lua.d/` user config, WirePlumber restarted) hands the HFP *control* role to oFono while PipeWire keeps the actual audio — this is a documented coexistence mode, not "building a separate audio stack." After this, oFono's profile registration succeeded and a real HFP modem for the iPhone appeared (`/hfp/org/bluez/hci0/dev_AC_45_00_3D_8A_4E`, `Type: hfp`, `Name: "Reyrubi Iphone"`).
3. Every real `Modem.SetProperty("Powered", true)` attempt to actually bring the call-control link up was refused by the phone at the Bluetooth link layer — three distinct, real error codes across four attempts: `org.bluez.Error.Failed: br-connection-page-timeout`, `bluetoothd`'s own `error updating services: Host is down (112)`, and `org.bluez.Error.NotAvailable: br-connection-profile-unavailable` (this last one reproduced twice, including **during an actual live phone call** placed specifically to rule out "iOS only opens HFP mid-call" as the cause — it made no difference).
   Conclusion: `UNAVAILABLE`, real result, not inferred — same MFi-accessory restriction as Contacts/Messages, one layer deeper (the profile-registration handshake succeeds, but the phone still refuses the actual service connection). `bluetooth_provider.probe_calls()` reports this as a fixed, documented research finding rather than a live per-call D-Bus probe, since re-testing it live would require oFono as a permanent dependency for a capability now confirmed non-functional against this exact device.
4. Host fully reverted after testing: `oFono` purged, the WirePlumber user override removed, WirePlumber restarted back onto its default native HFP/HSP backend — confirmed `wireplumber` active again post-restart, no lingering config.

**`probePhoneCapabilities(mac)`** (new `Backend` slot, wired to a "Test Phone Capabilities" button on the Bluetooth page) runs `probe_contacts`/`probe_messages`/`probe_calls` for real, off the UI thread, and renders the actual `AVAILABLE`/`UNAVAILABLE` + detail text per capability — this is the mechanism described above, not a hypothetical. Connection Diagnostics' Contacts/Messages/Calls rows now run the same real probes whenever an iPhone is paired (previously hardcoded `NOT_TESTED` unconditionally), and fall back to `NOT_TESTED` only when no iPhone is paired at all.

**Known caveat on this update**: the new `bluetooth_provider.probe_*()` functions are written against PySide6's `QtDBus` (matching this file's existing style) and are protocol-verified (the exact same `CreateSession`/`Select`/`GetSize` D-Bus calls were run for real via a throwaway `dbus-python` script against this same iPhone, producing the results above). The `QtDBus` wrapper code itself was synced to the Dev VM and actually imported/executed with real PySide6 (`from providers import bluetooth_provider as bt; bt.probe_calls()/probe_contacts()/probe_messages()`) — runs cleanly, no exceptions, correctly falls back to a clean `UNAVAILABLE`+detail when `org.bluez.obex`/the adapter aren't present (the VM's real state, no BT passthrough). What's *not* yet done: running `probePhoneCapabilities()` against a real adapter with this real iPhone actually connected end-to-end through the `QtDBus` code path specifically (as opposed to the equivalent raw `dbus-python` calls already proven above) — that needs PySide6 on the physical host, which isn't installed there. A real follow-up item, not silently assumed identical.

Per the spec's Definition of Done ("Messages and calls must remain hidden/disabled if the iPhone/BlueZ combination does not expose them"): Contacts, Calls, and Messages all now correctly resolve to `UNAVAILABLE` for this real iPhone via `probePhoneCapabilities()`/Connection Diagnostics — none of the three UI sections described in the original spec (Contacts search, an incoming-call dialog, a Messages conversation view) were built, because building them would be exactly the "fake functionality for visual completeness" the spec explicitly forbids. Only Battery is real and `AVAILABLE`.

**Two real bugs found and fixed during this testing pass** (both would have shipped broken without live GUI verification — code review alone did not catch either):
1. **Tailscale iOS client reports `HostName: "localhost"`** for every iPhone (a real quirk of Tailscale's own iOS app, not a ReyOS bug) — `tailscale_status()`'s original name-derivation logic (`HostName or DNSName`) picked the wrong field, silently breaking every "find the iPhone in the tailnet" lookup. Fixed by preferring `DNSName`'s first label, and by matching on the peer's `OS` field ("iOS") as a more reliable signal than name substring matching in `test_remote_connection()`.
2. **`vpn_provider.test_remote_connection()`'s `check_ssh` path had a broken import** — `from remote_provider import ssh_status` instead of `from providers.remote_provider import ssh_status` — silently threw `ModuleNotFoundError` inside the background worker thread, which was swallowed into an empty `{}` result and rendered as a confusing "Not ready yet" with zero visible checks. Only surfaced by clicking the real "Test Remote Connection" button in the live GUI with SSH-checking enabled (the default) and reading the app's own log file — a host-side script test that happened not to pass `check_ssh=True` completely missed it.

**Pre-existing findings in Control Center, out of scope to fix here but worth flagging**: `VpnPage.qml`'s WireGuard "Profiles" list silently shows empty for any profile that was imported but never started, because `/etc/wireguard` is `0700` root-owned and `Backend._compute_vpn_status()`'s bare `Path(...).glob(...)` swallows the resulting `PermissionError` into an empty list (confirmed live, `ls -ld /etc/wireguard` → `drwx------ root root`). Similarly, `_compute_vpn_status()`'s `sudo wg show interfaces` call has no matching NOPASSWD sudoers rule in `shellprocess_sudoers_reyos_menu.conf`, so from a GUI process with no controlling terminal it likely fails silently every time (same class of bug that file's own comments document for other unlisted commands) — `vpn_provider.wireguard_status()` avoids both problems by reading `systemctl list-units wg-quick@*` instead, which needs no root at all.
