## 2026-11-16 — Reyva Flatpak rebuilt automatically when Flathub updates its runtime (tools/reyva-flatpak/)

Follow-up to 2026-11-05: Reyva's PySide6 is tied to the exact Qt version it was built with, so every Qt point release in Flathub's `org.kde.Platform//6.11` stops the published Reyva (`undefined symbol: _ZN14QObjectPrivateC2E16QtPrivate_6_11_2`) until someone notices and rebuilds it (5 days last time). Owner picked automatic rebuilds over bundling Qt.

- **`tools/reyva-flatpak/rebuild.sh`** + daily user timer on the Ubuntu host (`install-timer.sh`, 08:00, catches up at boot). Rebuilds the published `/app/manifest.json` (same source, same version) when Flathub's runtime or PySide BaseApp commit differs from the published one, tests it, publishes only if it starts. Details: `flatpak/README.md` → Automatic rebuilds.
- **Limit found while building it:** Flathub's history shows the runtime moved to Qt 6.11.3 on 10-31 and the BaseApp only on 11-02. In such a gap no rebuild can start (the matching PySide doesn't exist yet), so the test fails, the owner gets a notification, and the script waits for the next Flathub change. The gap is Flathub's, not ours; closing it would need option 2 (bundling Qt).
- **Tested on the host:** `--force --dry-run` built 0.1.12 against the current runtime, imports OK (Qt 6.11.3), 30 s offscreen run. The same two checks on the published 0.1.11 against today's runtime both failed with the laptop's exact `undefined symbol` error, so the gate blocks a broken build. Full publish rehearsal against a RAM copy of the repo and a local bare git remote: signed, pruned 13 → last 3 commits (size unchanged), pushed, "live" check passed, and a user-style install with signature checking got the rebuilt 0.1.12. Rehearsal found two real bugs, fixed: git drops ostree's empty `refs/remotes` folder (prune failed on a fresh clone), and a cleanup trap turned every "up to date" run into exit 1 under `set -e`. Installed service run: "up to date", exit 0. No real rebuild has been published yet; the first one happens when Flathub next updates the runtime.

## 2026-11-16 — Kernel updates no longer take away the running kernel's drivers; "Restart needed" after a kernel update (reyos-base 1.1.0-11, control-center-gui 1.0.0-148, update-notifier 1.0.0-4)

Laptop report (2026-11-16): a DualShock 4 and an Xbox pad paired fine in Control Center → Bluetooth but ReyOS Games didn't see them. An update at 11:33 (two minutes after boot) had upgraded `linux` 7.2.11 → 7.3.4. Arch replaces the kernel package in place, so `/usr/lib/modules/7.2.11-arch1-1/` was deleted while 7.2.11 was still running: `modinfo: ERROR: Module hid_playstation not found` (same for `hid_microsoft`, `hid_sony`), the DS4's HID device had no driver and never got an `/dev/input/event*` node. Nothing told Rey to restart. Owner's request: an update must not delete files the running system needs, by default.

- **reyos-base 11** depends on Arch's `kernel-modules-hook` (extra, 0.1.7-3) and enables its `linux-modules-cleanup.service`. Before a kernel transaction it copies `/usr/lib/modules/$(uname -r)` aside and puts it back afterwards; the next boot removes copies no package owns. It works from `uname -r`, so it covers `linux` and `linux-lts` the same way. NVIDIA's DKMS module is saved too (the pre hook runs before `71-dkms-remove`). Arch's depmod hook regenerates `modules.dep` for the restored folder because it still has `modules.order`. The hook only works from the next kernel update on: the update that installs it can't use it yet.
- **Control Center 148**: new `kernel_status.py` (restart needed = the running kernel's `vmlinuz` belongs to no package; modules missing = no `modules.dep` for it). Updates page: banner "A new Linux kernel was installed…" with **Restart now**, and the restart dialog after an update says the same. Updates installed from the "Updates are ready" dialog (any page) now open a "Restart needed" dialog when the kernel changed, instead of the popup that disappears. **ReyOS Games**: "Controller drivers can't load until you restart" banner with Restart now when the running kernel's modules are gone (checked every minute).
- **update-notifier 4**: once per boot (stamped with `boot_id`), a "Restart needed" notification with a **Restart now** button whenever the kernel was replaced, whichever tool ran the update. It waits in its own transient user unit (`reyos-restart-notice`) so the 30-minute timer isn't held up, and stays on screen until answered (`--expire-time=0`): a timed-out Plasma popup is dropped with no history entry, leaving `notify-send --wait` waiting with no button.
- **Bluetooth page**: `Component.onDestruction` guards `backend` (`BluetoothPage.qml:70: TypeError: Cannot call method 'stopBluetoothScan' of null`). Not reproduced on the Dev VM (no Bluetooth adapter, and closing the window didn't trigger it with the old line); the scan can't outlive the page by more than 30 s anyway (`bluetoothctl --timeout 30`, dies with the app).
- **Tested on the Dev VM** (stable 2026/10/24, running `6.18.58-1-lts`): installed all three; the hook came in, cleanup service enabled. Fake kernel package upgrade with `KVER` pointing at it (the hook honours `KVER`): the "running" kernel's folder was restored, `modules.dep` regenerated, `modinfo -k <it> hid_playstation` found the driver (the exact laptop failure); `systemctl start linux-modules-cleanup` then removed it, and a real reboot ran the service cleanly with the real kernels untouched. Control Center and ReyOS Games screenshots with a faked `uname -r` show the banners; the notifier's notification appeared once per boot, and its Restart now button rebooted the VM. `tests/test_kernel_status.py` (4 tests). **Not done:** a real kernel upgrade (the Dev VM's jump to 2026/11/14 is a 1.8 GB download and the host had 2.8 GB free); the laptop's next kernel update is the real test.

## 2026-11-05 — Reyva Flatpak closed on launch after Flathub's Qt 6.11.3 runtime update; downloads ask where to save by default (Reyva 0.1.12)

Laptop report (2026-11-04): Reyva didn't open after a normal update. Flathub moved `org.kde.Platform//6.11` to Qt 6.11.3 on 2026-10-31 (commit `fb23e178`). Reyva 0.1.11 carries the PySide6 from `io.qt.PySide.BaseApp//6.11` as it was when it was built (Qt 6.11.2), and PySide6 links Qt's private API, which is tied to the exact Qt version: `ImportError: .../PySide6/QtCore.abi3.so: undefined symbol: _ZN14QObjectPrivateC2E16QtPrivate_6_11_2, version Qt_6_PRIVATE_API`. Every Flatpak user is hit, not just the laptop. Reproduced on the Dev VM: updating its runtime from `76fa01ac` (10-24) to `fb23e178` gave the same error.

- **Fix:** rebuilt against the BaseApp that Flathub now ships (6.11.3, commit `25537519`). No code change was needed for it. Dev VM on runtime `fb23e178`: 0.1.12 installed from the release bundle, opens example.com, renderer up, no import or Mojo errors.
- **Patch 0012 (laptop, Rey's request):** `askDownloadLocation` defaults to on (`main.py`). A `settings.json` that already says `false` is kept. Dev VM with no settings file: the Downloads window says "Asks where to save each file".
- Built in RAM on the Ubuntu host (disk at 1.9 GB free): a separate Flatpak installation via `FLATPAK_USER_DIR=/dev/shm/...` with Flathub's KDE SDK/runtime and the BaseApp, flatpak-builder `--state-dir` and build dir in `/dev/shm`. Only the signed export into `~/reyva-flatpak-work/site/repo` touches the disk (+180 MB). Testing a build from that separate installation on the host's own desktop doesn't work: the window never appears, and the host's Flatpak services report the app "not installed" because they only know the real installation. Test on the Dev VM instead.
- **This comes back with every Qt point release** in the 6.11 runtime: whenever Flathub updates `org.kde.Platform//6.11` and the BaseApp, Reyva has to be rebuilt the same day or it stops starting. To check: `flatpak remote-info flathub io.qt.PySide.BaseApp//6.11` (Version) against the Qt version Reyva was built with.
- Published: commits `496a616` (source) and `9aae1ae` (manifest pin), Flatpak repo `d6d1875` (commit `208110b3`), GitHub Release `reyva-flatpak-v0.1.12`. Same day, with patch 0012 only: `.deb` `reyos-browser-v0.1.0-128ubuntu1` (clean ubuntu:24.04 container: installs, runs 40 s as a normal user under Xvfb with no errors) and Windows `reyva-windows-v0.1.0.114` (workflow run 42136155653 passed: smoke test, Credential Manager, install/launch/uninstall). Website links updated (`c855578`, deployed to the Pi). The old `reyva-flatpak-v0.1.11`, `reyos-browser-v0.1.0-127ubuntu1` and `reyva-windows-v0.1.0.113` releases were deleted afterwards.

## 2026-11-02 — Stable check: Arch Archive download timeouts reported as a failed snapshot (tools/stable-snapshot/, GitHub #26, #27)

The weekly check of Arch snapshot 2026/10/31 (run 41307235414, issue #26) failed while pacman was still downloading: `mkinitcpio`, `kded` and `libmalcontent` stalled on archive.archlinux.org ("Operation too slow. Less than 1 bytes/sec transferred the last 10 seconds"), pacman gave up on the server ("too many errors"), and the transaction was never committed. No ReyOS package or QML check ran. The workflow still opened "FAILED: keep the current date", and promote.sh treats a FAILED title as a real result, so it would never have checked 10/31 again.

- **smoke-test.sh** downloads before it installs: `pacman -Syyuuw`, then `-Suu` from the cache; `-Sw` the reyos-* packages, then `-S`. Only download steps are retried: 4 attempts, 30/60/120 s apart, and only while the errors are network ones (too slow, timed out, connection reset/refused, DNS, HTTP 5xx). A 404, a signature/checksum/corrupted-package error, unsatisfiable dependencies, file conflicts, import or QML errors fail at once, even beside a timeout. The snapshot-exists probe retries no answer, and exits 2 only on a real 404. `ParallelDownloads` 5 → 3 (archive.archlinux.org is a single server: the `*.archive.pkgbuild.com` names don't resolve). The servers are unchanged: the one snapshot date for core/extra/multilib, reyos-local from Pages and the reyos-drivers release, no live mirrors. Exit status 0 passed / 75 not validated / 1 failed / 2 bad or missing date, plus a `smoke-summary.md` (result, retries, the relevant log lines).
- **Workflow**: three issue titles: "passed: ready to promote", "FAILED: keep the current date", "NOT TESTED: download failure, not validated" (and "NOT TESTED: the check didn't finish" if the job was cancelled or timed out). A rerun of a date edits and comments on that date's open issue instead of opening a second one. Issue body = the summary; full log + summary as the `smoke-log` artifact for 90 days; summary also on the run page. 60-minute job timeout. The date input goes through `env`, no longer straight into the shell script.
- **promote.sh** reads NOT TESTED titles: never promoted, not skipped as FAILED either; when the check it started ends NOT TESTED it says so in the log and the notification.
- `tests/test_stable_snapshot_smoke.py` (14 tests, real smoke-test.sh against a fake pacman/curl/import check): full pass, the generated pacman.conf (only the snapshot), timeouts that recover, a timeout that never stops (75, 4 attempts, nothing installed), checksum on download and on install, dependency failure, 404, 404 beside a timeout, a timeout during install (75, no retry), QML failure, archive unreachable, missing snapshot, bad date. Writing them caught two bugs in the first version: the FAILED summary dropped pacman's `:: unable to satisfy dependency` line, and a missing snapshot exited 1 instead of 2 (its `exit` ran in a pipe's subshell).
- **Rerun of 2026/10/31** (run 41495216514): downloads went through, then check-imports.py failed on `import yaml`. A false positive: pc_games.py imports yaml only to read Lutris game configs, and Arch's `lutris` depends on `python-yaml`; 10/24 had it through some other package, 10/31 doesn't. `yaml` is now on-demand like `lutris` (owner's choice, instead of a control-center-gui dependency).
