# ReyOS — Fixes Log

Real bugs found and fixed, with root cause. Newest first. See `bugs.md` for what's still open.

## Fresh installs could never update or install a package — broken pacman keyring (2026-08-18, user-reported on `ReyOS-Test`)

Control Center's "Full update" failed immediately: `warning: Public keyring is not found`, `error: keyring is not writable`, `error: required key missing from keyring`, `error: failed to commit transaction (unexpected error)`. This meant **no package could ever install or update on a fresh ReyOS install** — the most severe bug found this session.

Root cause: `unpackfs` copies the live ISO squashfs's already-initialized `/etc/pacman.d/gnupg` straight onto the target, including *runtime* state that only makes sense inside the live session — confirmed live UNIX-socket files (`S.dirmngr`, and presumably `S.gpg-agent`) sitting alongside the actual keyring data. Those sockets reference the live session's own `dirmngr`/`gpg-agent` processes, which don't exist once the target boots for real, and GnuPG gets confused trying to use them rather than failing cleanly.

Fixed by adding a new `shellprocess@pacman_keyring` job (`shellprocess_pacman_keyring.conf`) right after `unpackfs` in the exec sequence: wipes `${ROOT}/etc/pacman.d/gnupg` and reinitializes it fresh with `pacman-key --gpgdir ${ROOT}/etc/pacman.d/gnupg --init` + `--populate archlinux cachyos` — the same thing a manual Arch install does post-chroot, just via `--gpgdir` instead of `arch-chroot` to match this repo's existing shellprocess convention of operating on `${ROOT}` directly. Validated the module loads cleanly in the correct sequence position via `calamares -d` on the Dev VM (`CppJobModule "shellprocess@pacman_keyring" loading complete`, right between `unpackfs` and `machineid`).

**Second real bug found deploying the fix above**: the very first real-install test of the new job itself failed — `Command pacman-key --gpgdir ... --populate archlinux cachyos finished with exit code 1` / `ERROR: The keyring file /usr/share/pacman/keyrings/cachyos.gpg does not exist.` Root-caused live by relaunching Calamares over SSH with output redirected to a file (`calamares -d > captured.log 2>&1`, since the normal launch produces almost no output and the default log path Calamares docs reference doesn't exist on this build) and driving a real install while tailing it. `cachyos-keyring` was never actually in `reyos-iso/packages.x86_64` — the Dev VM only had it because of unrelated manual `pacman -S` installs accumulated over the VM's lifetime as a general workstation, which masked the gap in every "looks installed" check done from that VM. Since the live ISO and the installed target are the *same* unpacked squashfs, a package missing from `packages.x86_64` is missing everywhere, live session included. Fixed by adding `cachyos-keyring` to `packages.x86_64` (`archlinux-keyring` was already present transitively via the `base` group — confirmed by the error only naming `cachyos.gpg`, never `archlinux.gpg`).

**Third real bug, found after the second fix — the whole custom job was solving the wrong layer**: rebuilt, reinstalled, and "Full update" failed again with the *exact original* keyring errors. Diagnosed live via a terminal opened directly on the running ReyOS-Test desktop (`mount` output): `/etc/pacman.d/gnupg` is mounted as a **tmpfs** on every boot (`tmpfs on /etc/pacman.d/gnupg type tmpfs (rw,relatime,mode=755,...,noswap)`), via `etc-pacman.d-gnupg.mount`, a standard file shipped in `reyos-iso/airootfs/etc/systemd/system/` (needed because the squashfs itself is read-only). That means whatever the custom `shellprocess@pacman_keyring` job wrote to `${ROOT}/etc/pacman.d/gnupg` at install time was real at the time, but gets invisibly shadowed by a fresh empty tmpfs on every single boot thereafter — the job's work never survives to the first real boot, ever. The airootfs already ships the exact right fix for this: `pacman-init.service` (`Requires=`/`BindsTo=etc-pacman.d-gnupg.mount`, runs `pacman-key --init` then `--populate` on start) — but `systemctl status` showed it `disabled` on both the live session and the installed target. Confirmed live: manually `systemctl start pacman-init.service` succeeded completely (`--init` and `--populate` both `status=0/SUCCESS`) now that `cachyos-keyring` is present. Replaced the custom job's manual `pacman-key --gpgdir` script with a single line — `systemctl --root=${ROOT} enable pacman-init.service` — using the existing, already-correct mechanism instead of reinventing it. `reyos-calamares` bumped to `1.3.6-31`.

**Fourth real bug, found verifying the third fix — `systemctl --root=` silently no-ops in this context**: rebuilt, and this time captured a full `calamares -d` debug log of a genuine, complete install (previous confusion came from a premature `virsh destroy` that killed an install mid-exec-phase — see the GUI-automation gotcha about always screenshot-confirming "All done." before touching the VM). The captured log proved the entire 41-job exec sequence ran with zero failures, including job 12/41 (our `shellprocess@pacman_keyring`, which loaded and ran cleanly) and job 24 "Removing live user from the target system", job 28 "Create user \<name\>", job 31 "Set hostname ReyOS" — all real, all successful. (A side effect of rapid repeated test installs: the account got named `liveuser` on this particular run because that's what was typed into the Users page — not a removeuser/users-creation bug, just a naming coincidence with the live session's own `liveuser` account.) Despite the job running cleanly, `systemctl status pacman-init.service` on the booted target still showed `disabled`, and "Full update" still failed with the exact original keyring errors. So `systemctl --root=${ROOT} enable` silently fails to create the enablement symlink in Calamares' shellprocess execution context (not a real chroot or booted system) — no error reported, just a no-op. Fixed by dropping `systemctl --root` entirely and creating the exact symlink it's supposed to produce, directly: `mkdir -p ${ROOT}/etc/systemd/system/multi-user.target.wants` + `ln -sf /etc/systemd/system/pacman-init.service ${ROOT}/etc/systemd/system/multi-user.target.wants/pacman-init.service`. No dependency on systemctl's offline-root resolution logic at all. `reyos-calamares` bumped to `1.3.6-32`. **Not yet verified against a real install.**

## Lock screen and live-ISO desktop both showed the stock Plasma wallpaper, never ReyOS's (2026-08-17)

User-reported: after sleep/lock on a freshly installed system, and throughout the entire Calamares install on the live ISO, the background was still KDE's stock default ("Flow" — the blue paper-ribbon wallpaper), not ReyOS's Midnight Copper one. Reproduced live on `ReyOS-Test`: the VM's screen had gone idle-to-sleep on its own, and waking it showed the stock wallpaper on the KScreenLocker greeter; a saved screenshot from the earlier Calamares install session confirmed the same stock wallpaper behind the installer window the whole way through.

Two independent gaps, same underlying pattern (something sets the *desktop* wallpaper but nothing ever set anything else):

- **Lock screen (any installed system):** `reyos-apply-branding.sh`'s `apply_wallpaper()` only ever wrote the desktop wallpaper (`plasma-org.kde.plasma.desktop-appletsrc` via a live `qdbus6` script against `plasmashell`). `kscreenlockerrc`'s own wallpaper key (`[Greeter][Wallpaper][org.kde.image][General] Image=`) was never written anywhere — confirmed via `kreadconfig6` returning empty on Dev — so KScreenLocker's greeter fell back to its compiled-in stock background. Fixed by adding the `kwriteconfig6 --file kscreenlockerrc ...` write to `apply_wallpaper()` (bumped `BRANDING_VERSION` to `midnight-copper-3` so already-branded profiles pick it up on next Welcome run), and by shipping a static `/etc/skel/.config/kscreenlockerrc` in `reyos-themes` so brand-new Calamares-created users get it immediately without waiting on Welcome's exit-triggered script at all.
- **Live ISO during Calamares install:** `reyos-welcome` (the only thing that ever triggers `reyos-apply-branding.sh`) explicitly refuses to run at all on the live medium (`if Path("/run/archiso/airootfs").is_mount(): return`) — by design, since Calamares is what should run there instead. That means nothing ever applied any ReyOS branding to `liveuser`'s session, desktop wallpaper included. Fixed by adding a live-session-only autostart entry (`reyos-iso/airootfs/etc/skel/.config/autostart/reyos-live-wallpaper.desktop`, running `/usr/local/bin/reyos-live-wallpaper.sh`) that waits for `plasmashell`'s D-Bus service and then sets both the desktop and lock-screen wallpaper — shipped directly in `reyos-iso/airootfs` (not a package) so it only ever lands in the live squashfs's `liveuser` home via `useradd -m`, never on a real install.

Verified the lock-screen half live end-to-end on `ReyOS-Test`: deployed the updated `reyos-themes` package, re-ran the branding script, then locked the session via `qdbus6 org.kde.screensaver Lock` (env vars pulled from a live `plasmashell` process's `/proc/PID/environ`, same technique as prior session's plasmashell-crash fix) and screenshotted the greeter — now shows the correct Midnight Copper wallpaper.

Later the same day: rebuilt all 15 changed `reyos-*` packages, refreshed the local repo, and built a fresh ISO (`reyos-2026.08.17-x86_64.iso`) carrying this fix plus everything else pending. Ran a full real Calamares install against it on `ReyOS-Test` (erase disk, new `reyrubi` account) and confirmed both halves live: the desktop wallpaper behind the Calamares installer window was correctly Midnight Copper from the moment the live session started (previously it was the stock Breeze "Flow" wallpaper for the entire install), and after first login + Welcome, locking the session showed the same correct wallpaper on the greeter too. Both gaps are closed.

Also note: `ReyOS-Test`'s fresh install has `ufw` enabled with default-deny incoming (per the new `shellprocess_firewall.conf` Calamares module) and `sshd` disabled by default, exactly as designed. Both were turned on by hand this session (`systemctl enable --now sshd`, `ufw allow 22`) purely to get a reliable deploy/verify channel — left in place since the VM is disposable test infra and the user is actively using it, but this is a deliberate deviation from a real install's defaults, not a bug.

## ReyOS-Test wouldn't boot the attached install ISO at all — SCSI vs SATA CD-ROM (2026-08-17)

Attached `reyos-2026.08.17-x86_64.iso` to `ReyOS-Test` as a CD-ROM (`virsh attach-disk ... --type cdrom`, default SCSI bus) to run a full fresh install. Despite the domain's `<os>` boot order already listing `cdrom` before `hd`, the VM kept booting straight into the *old installed system* on `vda` (confirmed via `/proc/cmdline` showing a fixed `root=UUID=...`, not an archiso live boot). Neither resetting the domain's OVMF NVRAM (`cp OVMF_VARS_4M.fd` over the domain's vars file) nor switching to explicit per-device `<boot order='N'/>` elements fixed it. Root cause found by entering the OVMF firmware's own Boot Manager menu (hold `ESC` during POST via repeated `virsh send-key`): it listed no CD-ROM entry at all, only `UEFI Misc Device`/PXE/HTTP — this OVMF build doesn't reliably surface an El-Torito-bootable CD-ROM attached via SCSI as a UEFI boot option. Fixed by reattaching the same ISO on the domain's existing SATA controller (`bus='sata'` instead of `bus='scsi'`) — SATA/AHCI is what Q35 natively expects for optical media, and OVMF picked it up immediately.

Also confirmed a real installer gotcha along the way: `reyos-launch-installer`'s live-session check (`mountpoint -q /run/archiso/airootfs`) only guards against running on an *installed* system — it does nothing to help you find the installer if autostart didn't fire for some other reason. When the autostart entry didn't show a window, KRunner-style search (`Meta` key → type "calamares") surfaced "Install ReyOS" directly and launched it fine once actually on the live medium.

Ran a full real install end-to-end after the SATA fix (erase disk, `reyrubi`/`reyos-test` account, full unpack) — it appeared to restart mid-way through a long unattended gap and looped back to the live installer's Welcome page rather than finishing, cause not confirmed (no swap configured on the live session, 3.8GiB RAM, is one plausible contributor for an OOM-triggered reboot during the `unpackfs` step, but not verified against logs since the reboot lost them). The install had actually completed successfully by then, though — the CD-ROM was still attached with boot priority, so the post-install reboot looped back into the live ISO instead of the freshly installed disk. Removing the CD-ROM disk entirely (`virsh detach-disk` refuses on a running domain for `device='cdrom'`; had to destroy, edit the XML to drop the `<disk>` block, then redefine) let it boot the real installed system on the next start. If a future automated install needs to be unattended and reboot on its own, either eject/detach the ISO before the reboot happens or don't rely on boot-order alone to skip it.

## Local package repo had two divergent database files; ISO build installed stale packages (2026-08-17)

Rebuilding all changed `reyos-*` packages and running `mkarchiso` produced `error: target not found: reyos-browser`, even though `reyos-browser` was freshly built and present as a `.pkg.tar.zst` file in `~/reyos-build/local-repo/` on the Dev VM. Root cause: `reyos-iso/pacman.conf`'s repo section is named `[reyos-local]`, so pacman resolves it to `local-repo/reyos-local.db` — but `repo-add` had been invoked against `reyos.db.tar.gz` (a same-directory, differently-named, unrelated database that nothing actually reads). `reyos-local.db.tar.gz` was stale since 2026-08-14 and missing several packages (including `reyos-browser`) entirely, and held outdated versions of others (e.g. `reyos-themes-1.0.0-26` instead of -42, `reyos-control-center-gui-1.0.0-21` instead of -35). Fixed by re-running `repo-add reyos-local.db.tar.gz` against the newest `.pkg.tar.zst` for every `reyos-*` package present in `local-repo/` (computed by parsing filenames, not trusting either database's existing contents). `reyos.db.tar.gz` is dead weight now — harmless since unreferenced, but don't repo-add against it again; always target `reyos-local.db.tar.gz` for this project's local repo.

Also confirmed while investigating: `/boot/EFI/Linux/reyos-linux.efi` (the UKI removed as unused cruft in the duplicate-GRUB-entry fix earlier this session) is a normal, expected output of this system's `mkinitcpio` preset — it comes back on every `mkinitcpio -P` run (e.g. after a `reyos-plymouth` update, since Plymouth assets are baked into the initramfs). It's not one-off leftover debris; if the duplicate GRUB "ReyOS" chainload entry resurfaces after a future initramfs rebuild, this is why — rerun `grub-mkconfig` to pick it up again rather than re-diagnosing from scratch, or decide whether the UKI output should be disabled in the preset entirely.

Built `reyos-2026.08.17-x86_64.iso` end-to-end with this session's changes (Control Center launcher/header icons, App Launcher icon, default wallpaper, Plymouth splash logo) and 8 other packages that had pending changes from earlier sessions (reyos-browser, reyos-calamares, reyos-kde-customization, reyos-sddm, reyos-themes, reyos-welcome). Deployed to `ReyOS-Test` (copied to the host's `/var/lib/libvirt/images/`, attached as the VM's CDROM, `virsh destroy && virsh start`) and confirmed live via screenshot: fresh live-session hostname, all the new icons and wallpaper present in Control Center, the taskbar, and the panel launcher.

## Dev VM GRUB menu showed a duplicate standalone "ReyOS" entry (2026-08-17)

User-reported: the GRUB boot menu listed a third entry, "ReyOS", below "Advanced options for ReyOS Linux" — not present in `/boot/grub/grub.cfg`'s text (confirmed via repeated reads, including a full regenerate + `sync`), so it kept surviving `grub-mkconfig` reruns. Root cause: a leftover Unified Kernel Image (`/boot/EFI/Linux/reyos-linux.efi`, dated Jul 23) from the earlier standard-kernel migration session, never cleaned up after the switch to the traditional `vmlinuz`+`initrd` GRUB entries. Confirmed genuinely unused first (`bootctl status` → "systemd-boot not installed in ESP", `cat /proc/cmdline` on the running system showed the normal `/vmlinuz-linux` path, not the UKI) before removing the file, regenerating `grub.cfg`, and confirming live that the menu is back to the correct 3 entries (`ReyOS Linux` / `Advanced options for ReyOS Linux` / `UEFI Firmware Settings`). Dev-VM-local cleanup only — installed systems use the Limine chain, not this GRUB+UKI combination, so this isn't a product bug.

Assumed Calamares' shellprocess module was matching `${VAR}` specifically as a global-storage placeholder it must resolve, and that a local variable sharing that syntax would collide. Fix attempt: dropped the braces (`$CMDLINE`). Rebuilt, reran — **identical failure**, same exact error text.
2. **Real but separate bug found while chasing #1: `repo-add` was targeting the wrong file.** `pacman.conf`'s `[reyos-local]` repo has `Server = file:///home/reyrubi/reyos-build/local-repo`, but pacman derives the actual database filename from the *repo name*, not the `Server=` path — the real file is `reyos-local.db.tar.gz`. Two rebuild attempts had been running `repo-add local-repo.db.tar.gz ...` (a file pacman never reads at all), so the "fixed" package was never actually reaching the ISO — confirmed by SSHing into the freshly-booted live ISO and finding `pacman -Q reyos-calamares` still reporting the old `pkgrel`. Always verify the exact repo name via `grep '^\[' pacman.conf` before running `repo-add` on any new/renamed repo.
3. **Real root cause, confirmed once #2 was fixed and the brace-only rebuild was genuinely deployed and still failed identically:** Calamares' shellprocess `CommandList` scans the *entire* script text for placeholders needing global-storage substitution, and matches **both** `${VAR}` and bare `$VAR` forms — braces are not what triggers it. Any token shaped like a shell variable reference is treated as a required global-storage key, and `CMDLINE` was never one (it's purely local to the script), so Calamares always rejected the job before even running it, regardless of brace style. Real fix: eliminated the intermediate `CMDLINE=$(...)` variable entirely and inlined the `$(grep ...)` command substitution directly into the heredoc's `cmdline:` line — command substitutions (`$(...)`) are not matched by Calamares' placeholder scanner (confirmed: the job's other genuinely-required `${ROOT}` substitution, and the original script's own `$(grep ...)`, never triggered the scanner). Fixed in `reyos-calamares` 1.3.6-4.

**Verified for real** on the third rebuild (`reyos-2026.08.11-x86_64.iso`, package 1.3.6-4): all 36 exec-phase jobs passed with zero errors, and a real reboot off `ReyOS-Test`'s installed disk landed cleanly on SDDM → login → working KDE Plasma desktop. This is the first time a rebuilt (not hand-patched) ReyOS ISO has completed a real install and reboot end-to-end. See `whats-next.md`.

**Also found, not yet fixed (see `bugs.md`):** the installed system's SDDM logs `Authentication error: User not known to the underlying authentication module` / `Autologin failed!` on every boot — `/etc/sddm.conf.d/` is copied verbatim from the live ISO via `unpackfs` and still references autologin for `liveuser`, which Calamares' `removeuser` job deletes during install. Harmless — SDDM correctly falls back to its normal greeter — but worth cleaning up.

**Also found, cosmetic:** the boot-splash tagline reads "BUILT FOR PERPORMANCE" instead of "PERFORMANCE" — confirmed on both the live ISO's boot splash and the freshly-installed system's first-login Plasma splash (same asset). The `ReyOS Welcome` app's own copy of the tagline is spelled correctly, so this is isolated to the plymouth/ksplash splash asset specifically.

## Installed system's initramfs was silently built with the live ISO's own archiso hooks (2026-08-10)
The "device did not show up after 30 seconds" boot failure logged in the previous entry as "possibly transient" was not transient — it reproduced on 2 of 3 subsequent real boots. Root-caused by mounting the installed disk from the live ISO and running `mkinitcpio -P` again by hand inside an `arch-chroot`, watching exactly which hooks it built with: `unpackfs` copies the *entire* live squashfs onto the target verbatim, which includes two files that only make sense on the live ISO itself:

1. `/etc/mkinitcpio.d/linux.preset` — the live ISO ships the **archiso** preset for the `linux` package (`PRESETS=('archiso')`, `archiso_image="/boot/initramfs-linux.img"`, pointed at `archiso_config='/etc/mkinitcpio.conf.d/archiso.conf'`), not the standard `default`/`fallback` preset a real install needs.
2. `/etc/mkinitcpio.conf.d/archiso.conf` — a mkinitcpio drop-in. mkinitcpio auto-merges *every* file under `mkinitcpio.conf.d/` regardless of what the preset points at, so even after fixing #1 alone, a chroot rebuild still logged `Using drop-in configuration file: archiso.conf` and built the exact same wrong hook set (`archiso archiso_loop_mnt archiso_pxe_common archiso_pxe_nbd archiso_pxe_http archiso_pxe_nfs memdisk udev` — no `systemd`/`autodetect`/`sd-vconsole`/`fsck`). Confirmed by inspecting the resulting image directly (`lsinitcpio`) before and after: the "broken" image was 245MB (an archiso-flavored image bundles tooling for finding/mounting a live squashfs across every possible boot medium — USB/PXE/NFS/CD); after removing both files and rebuilding, `/boot/initramfs-linux.img` dropped to 16MB and correctly used `base systemd autodetect microcode kms modconf block keyboard sd-vconsole filesystems fsck` — the real `/etc/mkinitcpio.conf`.

Calamares' own `initcpio` job (`mkinitcpio -P` in the target chroot) was never actually broken — it succeeded every single install, just building the wrong image because these two leftover files silently outrank the target's real config. Fixed with a new `shellprocess@fix_mkinitcpio_preset` job (deletes the drop-in, restores the standard `linux` package preset) placed before `initcpiocfg`/`initcpio` in the exec sequence. Verified two ways on the same already-installed `ReyOS-Test` disk rather than a full reinstall: manually applied the fix + `arch-chroot ... mkinitcpio -P` from the live ISO, confirmed the correct hook set and image size, then rebooted off the disk — landed cleanly on SDDM with no panic, first genuinely reliable real boot.

## Installed system boots for real, first time ever — four chained bugs found and fixed via live-patch-then-verify on ReyOS-Test (2026-08-10)
Picked up from `a482394`'s unverified bootloader chain (limine binary, target db sync). Running one more real install immediately hit a **fifth** bug in that same chain, then three more after it — each only found by actually running a real install and, at the end, actually rebooting the target disk. Iterated by hand-patching the live ISO session's `/etc/calamares/*` files directly and re-running the installer (no ISO rebuild needed per iteration — much faster feedback loop), only porting each fix back into the `reyos-calamares` package source in git once confirmed working. All four are now committed to the package source; **not yet baked into a rebuilt ISO** — see `whats-next.md`.

1. **`shellprocess@sync_target_db`'s `pacman -Sy` couldn't resolve any mirror hostname inside the chroot.** `unpackfs` is not `pacstrap` — pacstrap copies the host's `/etc/resolv.conf` into a fresh target automatically as part of what it does; a plain squashfs extraction does not. Fixed by adding `dontChroot: true` plus an explicit `cp /etc/resolv.conf ${ROOT}/etc/resolv.conf` before the chrooted `pacman -Sy` call — same pattern `cachyos-calamares`'s own `shellprocess_initialize_pacman.conf` uses for the identical reason.
2. **That `cp` itself then failed: `'/etc/resolv.conf' and '/tmp/calamares-root-.../etc/resolv.conf' are the same file`.** The squashfs's own `/etc/resolv.conf` is an *absolute* symlink to `/run/systemd/resolve/stub-resolv.conf`. Run un-chrooted (required for fix #1), that absolute symlink resolves against the *live* root on both the source and destination side of the `cp`, so they're literally the same inode and `cp` refuses, copying nothing. Fixed by `rm -f ${ROOT}/etc/resolv.conf` immediately before the `cp`, so the destination is a plain path with no symlink left to chase back to the live root.
3. **With DNS now genuinely working, `pacman -S limine-mkinitcpio-hook` still failed: `target not found`.** That package does not exist anywhere in the official Arch repos — confirmed via `pacman -Si`/`-Ss`/`-Qo`/`-Ql` all coming back empty. The entire premise behind `a482394`'s fix (that installing this package provides `/usr/bin/limine-install`) was wrong from the start; current `limine` (12.5.2, official `[extra]`) dropped the installer script years ago. Its own shipped `USAGE.md` documents the real modern UEFI install method: copy `BOOT*.EFI` straight into the ESP's `/EFI/BOOT/` directory, no separate installer needed at all. Fixed two ways: (a) removed the whole `packages@offline` job and its `packages_offline.conf` (nothing else needed installing at this stage, so once the fake package need was gone the job did nothing) — this also made fix #1/#2's `sync_target_db` job itself unnecessary, so both are deleted from the sequence and the package source entirely; (b) added a tiny `shellprocess_limine_shim.conf` (`dontChroot: true`) that writes a real `/usr/bin/limine-install` shim script into the target doing exactly the documented copy, so `cachyos-calamares`'s otherwise-correct `bootloader` module call succeeds without forking/patching their vendored `main.py`.
4. **With the shim in place, `bootloader` succeeded but the system still panicked on boot: `PANIC: Boot protocol not specified for this entry`.** Read `cachyos-calamares`'s `update_limine_config()` directly (`/usr/lib/calamares/modules/bootloader/main.py`): it writes the boot entry *header* (`comment: machine-id=...` / `/+CachyOS`) but never writes the entry *body* (`protocol:`/`kernel_path:`/`module_path:`/`cmdline:`). On real CachyOS that body is filled in later by a pacman hook shipped inside — the same nonexistent `limine-mkinitcpio-hook` from bug #3 — triggered every time mkinitcpio regenerates the initramfs. ReyOS has nothing that ever writes it. The values needed *are* already written by Calamares itself, to `/etc/default/limine` (`KERNEL_CMDLINE[default]+="..."`), just never consumed by anything. Fixed with a new `shellprocess_limine_entry.conf` job, run right after `bootloader`, that greps the real cmdline out of `/etc/default/limine` and appends the missing `protocol: linux` / `kernel_path: boot():/vmlinuz-linux` / `module_path: boot():/initramfs-linux.img` / `cmdline: ...` block directly to `limine.conf`.

**Verified for real**: manually applied fix #4 to an already-Calamares-installed `ReyOS-Test` disk (rather than reinstalling again) via the live ISO session, unmounted, flipped the domain's boot order to `hd,cdrom`, and rebooted. First reboot attempt hit a *separate*, likely transient issue — mkinitcpio's `ERROR: '' device did not show up after 30 seconds` dropping to the emergency shell, even though `blkid`/`cat /proc/cmdline` inside that same emergency shell showed the correct root UUID and a real matching block device — not yet root-caused, see `bugs.md`. A second boot attempt immediately after (no changes made) **booted cleanly all the way to the desktop**, autologin working, `ReyOS Welcome` (the first-login wizard, which only ever fires for a genuinely new user account — proof this wasn't the live ISO) rendering correctly. This is the first time in the project's history a Calamares-installed ReyOS system has booted for real.

## Calamares exec-phase scoping found two stale-path bugs inherited from cachyos-calamares (2026-08-09)
Wiring up the real (disk-writing) exec phase meant reading cachyos-calamares's own module configs as a reference baseline, rather than writing the sequence from scratch — but its `unpackfs.conf` (the module that copies the live squashfs onto the target disk) has two hardcoded assumptions that don't hold for ReyOS: `source: "/run/archiso/bootmnt/arch/x86_64/airootfs.sfs"` assumes `install_dir="arch"` in `profiledef.sh`, but ours is `"reyos"` — so the real path is `reyos/x86_64/airootfs.sfs`. Same file also copies `vmlinuz-linux-cachyos`, but `packages.x86_64` ships the plain `linux` kernel, not `linux-cachyos` — real filename is `vmlinuz-linux`. Both confirmed against a real build's `work/iso/reyos/` tree on the dev VM, not guessed. Fixed via a `unpackfs.conf` override in `reyos-calamares` (same pacman-hook staging pattern as `users.conf`). Its `grubcfg.conf` had the analogous `GRUB_TOP_LEVEL: "/boot/vmlinuz-linux-cachyos"` bug plus a `GRUB_THEME` pointing at a CachyOS-only theme path that doesn't exist on ReyOS — fixed the kernel path, dropped the theme reference until `reyos-grub` is actually wired into the base image.

ReyOS's own `packages.x86_64` already bakes `plasma-desktop` and every `reyos-*` branding package into the live squashfs at ISO-build time, so the offline/unpackfs model gives a fully ReyOS-branded real install with no separate base-package list to maintain in Calamares — the online model would have meant hand-curating and keeping a second package list in sync. Adapted ReyOS's `settings.conf` from the offline reference, dropping three CachyOS-only `shellprocess` steps (`shellprocess-before`, `shellprocess`, `shellprocess_enable_ufw`) that invoke helper scripts (`/usr/local/bin/remove-nvidia`, `dmcheck`, `/etc/calamares/scripts/shell-setup`, `bootloader-post-setup`) which only exist because cachyos-calamares's `pacstrap.conf` copies them in via `postInstallFiles` — since ReyOS uses unpackfs instead of pacstrap, those files never land on the target, and at least one of those script invocations has no `-` (non-fatal) prefix, meaning it would hard-fail the whole install if included. Validated the resulting sequence by launching Calamares in debug mode (`calamares -d`) on the dev VM: all 20+ modules load without error, 8 view steps register, only "requirement not satisfied: partitions" — which is correct, since the dev VM's own root disk is safely filtered out as an install target (0 suitable devices), same as it would be for any live system with no spare disk. Not yet tested against a real target disk — see `bugs.md`/`whats-next.md`.
